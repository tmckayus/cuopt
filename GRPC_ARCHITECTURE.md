# gRPC Interface Architecture

## Overview

The cuOpt remote execution system uses gRPC for client-server communication. The interface
supports arbitrarily large optimization problems (multi-GB) through chunked streaming,
and provides robust error handling with automatic retries.

All serialization uses protocol buffers generated by `protoc` and `grpc_cpp_plugin` -
no custom serialization logic is implemented.

## Protocol Files

| File | Purpose |
|------|---------|
| `cuopt_remote.proto` | Message definitions (problems, settings, solutions) |
| `cuopt_remote_service.proto` | gRPC service definition (RPCs) |

Generated code is placed in the CMake build directory (not checked into source).

## Service Interface

```protobuf
service CuOptRemoteService {
  // Job submission
  rpc SubmitJob(SubmitJobRequest) returns (SubmitJobResponse);
  rpc UploadAndSubmit(stream UploadJobRequest) returns (stream UploadJobResponse);

  // Job management
  rpc CheckStatus(StatusRequest) returns (StatusResponse);
  rpc CancelJob(CancelRequest) returns (CancelResponse);
  rpc DeleteResult(DeleteRequest) returns (DeleteResponse);

  // Result retrieval
  rpc GetResult(GetResultRequest) returns (ResultResponse);
  rpc StreamResult(GetResultRequest) returns (stream ResultChunk);

  // Blocking wait (returns status only, use GetResult afterward)
  rpc WaitForCompletion(WaitRequest) returns (WaitResponse);

  // Real-time streaming
  rpc StreamLogs(StreamLogsRequest) returns (stream LogMessage);
  rpc GetIncumbents(IncumbentRequest) returns (IncumbentResponse);
}
```

## Streaming Protocol

### Why Streaming?

gRPC has per-message size limits (default 4 MiB, often configured to 256 MiB). Optimization
problems can exceed several gigabytes, so chunked streaming is required.

### Upload Protocol (`UploadAndSubmit`)

Bidirectional streaming RPC for uploading large problems:

```
Client                              Server
  |                                   |
  |-- UploadStart (problem_type) ---> |
  |<-- UploadAck (committed_size) --- |
  |                                   |
  |-- UploadChunk (offset, data) ---> |
  |<-- UploadAck (committed_size) --- |
  |                                   |
  |-- UploadChunk (offset, data) ---> |
  |<-- UploadAck (committed_size) --- |
  |           ...                     |
  |                                   |
  |-- UploadFinish --------------->   |
  |<-- SubmitJobResponse (job_id) --- |
```

**Key features:**
- Each chunk is acknowledged with `committed_size`
- Server reports `max_message_bytes` in acknowledgments
- Client can resume from `committed_size` on reconnection
- Upload ID allows tracking across retries

### Download Protocol (`StreamResult`)

Server-side streaming for retrieving large results:

```
Client                              Server
  |                                   |
  |-- GetResultRequest (job_id) ----> |
  |                                   |
  |<-- ResultChunk (offset, data) --- |
  |<-- ResultChunk (offset, data) --- |
  |           ...                     |
  |<-- ResultChunk (done=true) ------ |
```

**Key features:**
- Chunks include offset for reassembly
- Final chunk has `done=true`
- Each chunk can include `error_message` for early failure detection

## Error Handling

### gRPC Status Codes

The service uses standard gRPC status codes:

| Code | Meaning | Client Action |
|------|---------|---------------|
| `OK` | Success | Process result |
| `NOT_FOUND` | Job ID not found | Check job ID |
| `RESOURCE_EXHAUSTED` | Message too large | Use streaming |
| `CANCELLED` | Job was cancelled | Handle gracefully |
| `DEADLINE_EXCEEDED` | Timeout | Retry or increase timeout |
| `UNAVAILABLE` | Server not reachable | Retry with backoff |
| `INTERNAL` | Server error | Report to user |
| `INVALID_ARGUMENT` | Bad request | Fix request |

### Automatic Streaming Fallback

The client automatically handles size limits:

1. **Submit**: Try unary `SubmitJob` first
2. If `RESOURCE_EXHAUSTED`: Fall back to `UploadAndSubmit` streaming
3. **Result**: Check `result_size_bytes` from status
4. If exceeds limit: Use `StreamResult` instead of `GetResult`

### Upload Retry Logic

When `UploadAndSubmit` fails:

1. Check `UploadError.committed_size` to see progress
2. Read `max_message_bytes` from error response
3. Reduce chunk size by 50%
4. Retry from last committed offset
5. Give up after `max_upload_retries` (default: 2)

### Connection Handling

- Client detects `context->IsCancelled()` for graceful disconnect
- Server cleans up job state on client disconnect during upload
- Automatic reconnection is NOT built-in (caller should retry)

## Completion Strategies

The client supports two strategies for waiting until a job completes:

### Polling (default)

```cpp
config.use_wait = false;  // default
```

- Main thread polls `CheckStatus` every `poll_interval_ms`
- Detects completion when status changes to COMPLETED/FAILED/CANCELLED
- Allows timeout detection (max_polls = timeout_seconds / poll_interval_ms)
- Compatible with all server configurations

### Wait RPC

```cpp
config.use_wait = true;
```

- Main thread makes single blocking `WaitForCompletion` call
- More efficient (no repeated RPCs)
- Server blocks until job completes, then returns final status
- Result must still be fetched separately via `GetResult`/`StreamResult`

Both strategies support concurrent log streaming and incumbent callbacks - these
run in background threads independent of the main completion check.

## Client API (`grpc_client_t`)

### Configuration

```cpp
struct grpc_client_config_t {
  std::string server_address = "localhost:9112";
  int poll_interval_ms       = 500;
  int timeout_seconds        = 3600;
  bool use_wait              = false;  // Use WaitForCompletion instead of polling

  // Streaming configuration
  int64_t max_message_bytes = 256 * 1024 * 1024;  // 256 MiB
  int64_t chunk_size_bytes  = 1 * 1024 * 1024;    // 1 MiB
  int max_upload_retries    = 2;

  // TLS configuration
  bool enable_tls = false;
  std::string tls_root_certs;   // CA certificate (PEM)
  std::string tls_client_cert;  // Client certificate (mTLS)
  std::string tls_client_key;   // Client private key (mTLS)

  // Callbacks
  std::function<void(const std::string&)> log_callback;
  std::function<bool(int64_t, double, const std::vector<double>&)> incumbent_callback;
};
```

### Synchronous Operations

```cpp
// Blocking solve - handles streaming automatically
auto result = client.solve_lp(problem, settings);
auto result = client.solve_mip(problem, settings, enable_incumbents);
```

### Asynchronous Operations

```cpp
// Submit and get job ID
auto submit = client.submit_lp(problem, settings);
std::string job_id = submit.job_id;

// Poll for status
auto status = client.check_status(job_id);

// Get result when ready
auto result = client.get_lp_result<int, double>(job_id);

// Cancel or delete
client.cancel_job(job_id);
client.delete_job(job_id);
```

### Real-Time Streaming

```cpp
// Log streaming (callback-based)
client.stream_logs(job_id, 0, [](const std::string& line, bool done) {
  std::cout << line;
  return true;  // continue streaming
});

// Incumbent polling (during MIP solve)
config.incumbent_callback = [](int64_t idx, double obj, const auto& sol) {
  std::cout << "Incumbent " << idx << ": " << obj << "\n";
  return true;  // return false to cancel solve
};
```

## TLS Configuration

### Server-Side TLS

```bash
./cuopt_grpc_server --port 9112 \
  --tls \
  --tls-cert server.crt \
  --tls-key server.key
```

### Mutual TLS (mTLS)

Server requires client certificate:

```bash
./cuopt_grpc_server --port 9112 \
  --tls \
  --tls-cert server.crt \
  --tls-key server.key \
  --tls-root ca.crt \
  --require-client-cert
```

Client provides certificate:

```cpp
config.enable_tls = true;
config.tls_root_certs = read_file("ca.crt");
config.tls_client_cert = read_file("client.crt");
config.tls_client_key = read_file("client.key");
```

## Message Size Limits

| Configuration | Default | Notes |
|---------------|---------|-------|
| gRPC default | 4 MiB | Too small for cuOpt |
| Server `--max-message-mb` | 256 MiB | Per-message limit |
| Client `max_message_bytes` | 256 MiB | Should match server |
| Chunk size | 1 MiB | Safe default for streaming |

**Important:** Streaming allows unlimited total payload size; only individual
chunks must fit within the per-message limit.

## Security Notes

1. **No Custom Serialization**: All message parsing uses protobuf-generated code
2. **Standard gRPC Security**: HTTP/2 framing, flow control, standard status codes
3. **TLS Support**: Optional encryption with mutual authentication
4. **Input Validation**: Server validates all incoming messages before processing
